# ACCEPTANCE TODO — приёмка старых CODE READY

Срез четырёх основных разделов [MASTER_TODO](MASTER_TODO.md) на `508b323c6a8cfa73d0da9017bb7e43314d59534f`: 380 уникальных родительских ID CODE READY. Это отдельная очередь практической приёмки, не новые дефекты и не новые ID. Строки AGR/ARCH и исторический повтор SMALL_TASKS не входят в этот срез: их вести по действующим профильным критериям и EXECUTION_TODO. Исходные требования — MASTER_TODO и профильный TODO; колонка «Остаток приёмки» перенесена из MASTER на момент среза, не заменяет полный критерий. [Исходный снимок](https://github.com/xBonkx/CsharpGMC/blob/508b323c6a8cfa73d0da9017bb7e43314d59534f/docs/MASTER_TODO.md).

## Как работать

- Взять 20–30 связанных свободных ID за проход, если реально возможно; P0/P1 прежде P2. Это объём проверки, не квота формальных DONE. Разделять реальную приёмку и статическую сверку. Доказательства можно переиспользовать для нескольких ID, только если они покрывают каждый критерий, с указанием SHA, конфигурации, фактического запуска и результата.
- Сначала изучить точные критерии родителя, прежние доказательства и текущую реализацию. Запустить необходимые проверки на реальной сборке: Windows/WPF/DPI/SQL Pilot/экспорт/замеры по конкретному ID. Build, xUnit и чтение исходников не заменяют требуемый UI, SQL или performance сценарий. Сохранять артефакты/логи и краткую ссылку на единый отчёт, не копировать его во все TODO.
- DONE только при полном фактическом выполнении исходных критериев; при неполной приёмке оставить CODE READY, при известном дефекте PARTIAL, при невозможности BLOCKED с конкретным условием возобновления. В очереди IN PROGRESS обозначает только бронь, родитель в MASTER остаётся в исходном статусе до результата. После исправления повторить затронутые проверки. Не удалять строки: сохранять историю DONE/возвратов, не считать их открытыми.
- Только Microsoft SQL Server; разрешённые изолированные GmcSmetaPilot_*; рабочие БД/Cutover не трогать. Demo — только в отдельно разрешённом локальном тестовом режиме. Не менять DDL без согласования, не отключать гварды, не обходить падающие тесты, не публиковать релизы. Для разрушительных сценариев отдельная разрешённая копия, не общая demo-БД.
- Раздельные Git worktree, obj/bin и профили для локальных агентов; не совмещать нагрузочные измерения с тяжёлыми тестами, не запускать конфликтующие тесты на одном экземпляре/БД/GUI. Если ресурс нужен эксклюзивно, указывать его в scope брони. Не делать git checkout/reset чужих рабочих файлов.

## Бронь — обязательна до проверки или правок

**Единственный реестр броней старых CODE READY — этот файл.** Запрещено создавать параллельные таблицы занятости. [План perfacc-A](CODE_READY_ACCEPTANCE_20261129.md) сохраняет исходные критерии и кампании, но не является отдельным реестром. 30 исходных броней zcode-sess-perfacc перенесены без изменения владельца и статуса; освобождает их только этот агент/координатор по обычному правилу. Активные ресурсы сверять также с EXECUTION_TODO: если другой агент уже использует тот же SQL/GUI/benchmark стенд, согласовать непересекающиеся интервалы/ресурсы до прогона, не освобождать чужую бронь. Если в старом плане появились новые результаты после переноса, не повторять проверку: сверить evidence с владельцем и актуализировать только каноническую строку.

1. Получить свежий origin/main, прочитать **обе** очереди: эту и [EXECUTION_TODO](EXECUTION_TODO_20261128.md). Сверить ID, родителя/детей, зависимости, файлы и эксклюзивные ресурсы (SQL test DB, профили, desktop/DPI, измерительный стенд). Не брать чужие ☑ или пересекающиеся scope; для совместимого read-only явно указать read-only и не менять файлы без обновления брони.
2. В этой таблице поставить IN PROGRESS и `☑ unique-agent-id / UTC / branch / expected file/module + resource scope / prior=CODE READY` (либо точный прежний статус для возврата), обновить фактическую сводку. Отдельный коммит меняет **только ACCEPTANCE_TODO.md**. Fast-forward push без force / API expected_sha. При изменении head перечитать обе очереди и повторить выбор; после push перечитать main и подтвердить свои строки. Без подтверждённой брони не начинать проверки/правки.
3. При расширении scope сначала обновить бронь. Если выяснилось, что нужен пакет EXECUTION_TODO, согласовать его с владельцем той брони; не исправлять поверх чужой работы. При обнаружении нового непокрытого дефекта вернуть родителя PARTIAL и добавить конечный пакет в EXECUTION_TODO с ссылкой на этот ID; эта строка приёмки остаётся PARTIAL и не бронируется до завершения дочерней работы. Не держать активные брони одного родителя в двух очередях одновременно.
4. Финальным коммитом снять только свои ☑, вернуть ☐, записать итог, доказательство, обновить MASTER, профильный TODO и CURRENT_TASK, сводки по фактическим строкам. При прерывании снять свою бронь и восстановить прежний статус либо PARTIAL/BLOCKED с причиной. Не снимать чужую бронь по возрасту; только по подтверждению владельца/координатора.
5. Если новый родитель стал CODE READY после среза, исходные дочерние T/A ещё выполняются в EXECUTION_TODO. Не дублировать. Когда дочерняя очередь исчерпана, но необходима дополнительная приёмка, добавить сюда тот же родительский ID (если его ещё нет); не включать исторические дубли. При повторном открытии DONE — вернуть фактический статус с причиной и новой проверкой.
6. В отчёте: взято, DONE, осталось CODE READY, PARTIAL/BLOCKED, активные брони, фактические проверки, SHA, дефекты и ограничения. Отдельно от новой очереди, не складывать с MASTER как дополнительные задачи.
