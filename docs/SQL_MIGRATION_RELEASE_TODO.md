
# Одна кнопка: выпуск релиза и миграция SQL Server

## Решение владельца от 25.11.2026
EXE «ГМЦ-Смета — собрать релиз» выполняет весь процесс одним нажатием.
Если схема не изменена, SQL Server не трогается. Если схема изменилась,
выпуск включает миграцию с резервной копией, без ручного набора команд.

## Текущее состояние / блокер
Обычная запись C# разрешена только на схеме 28. Схема 31 допускается
в отдельных preview/write-test режимах, а полноценный переход 28 → 31
владелец поручает Codex отдельно. SQLite Migrations.cs не применим к SQL Server.
Production Cutover по-прежнему запрещён; ограничения не снимать автоматически.
Сейчас релизный guard останавливает выпуск, если WritableSchemaVersion
отличается от approved-schema.txt. Это временная блокировка, не мигратор.
Не менять approved-schema.txt ради обхода. sql-schema-version.txt включён
в релиз и SHA256SUMS.

## Задание для Codex: закончить интеграцию
- [ ] Сверить DDL, модели Python и SQL Server 28/31, все денежные расчёты,
      скидки, КС, права и чтение/запись. Подготовить конкретные SQL-скрипты
      перехода 28 → 31 и последующие явные последовательные миграции.
- [ ] Сделать управляемый администратором профиль сервера/БД для выпуска:
      точная идентификация сервера и каталога, безопасные учётные данные,
      без передачи паролей в аргументах, логах и Git. Сначала только отдельная
      восстановленная копия. Production разрешать отдельным согласованным cutover.
- [ ] Сохранить однокнопочный сценарий: подтянуть чистый main → сборка →
      обязательные тесты → упаковка → загрузить проверенные файлы в DRAFT →
      проверка фактической schema_version → при необходимости обслуживание →
      полный резервный backup → проверка → миграция → проверки → публикация DRAFT.
      Не публиковать и не делать latest до подтверждения результата миграции.
      Не удалять старые релизы и не запускать миграцию у каждого сотрудника.
- [ ] Если фактическая схема совпадает с целевой, никакого BACKUP/DDL. Если
      схема неизвестна/новее или нет полного утверждённого маршрута — остановить.
      После включения мигратора заменить временный guard проверкой манифеста,
      не повышать approved-schema.txt без полноценной приёмки.
- [ ] При миграции до публикации нужна согласованная остановка записи ВСЕХ
      клиентов Python и C#, включая старые версии. Исключить гонки между
      издателями; использовать серверную блокировку и окно обслуживания.
      Не завершать сеансы с несохранёнными данными принудительно.
- [ ] SQL Server: уникальный полный BACKUP DATABASE WITH COPY_ONLY, CHECKSUM
      в серверное хранилище. RESTORE VERIFYONLY WITH CHECKSUM обязательно.
      Проверить место и права; при неудаче никакого DDL. Сохранить .bak и журнал.
- [ ] Миграции транзакционные, проверить исходную и итоговую схемы,
      количество строк, ключи, целостность и контрольные суммы финансовых
      отчётов. schema_version обновлять в той же транзакции. При ошибке rollback
      и запрет публикации. Не делать автоматический RESTORE поверх рабочей БД.
- [ ] Реально восстановить .bak в новую отдельную БД и сверить данные.
      Проверить сбой процесса/сети после commit до публикации: журнал состояния,
      повторный запуск не повторяет выполненные шаги, продолжает выпуск
      проверенного черновика; предусмотреть безопасный откат и совместимость.
- [ ] GUI: этапы «Схема БД», «Резервное копирование», «Миграция», «Проверка»,
      название БД, версии схемы, путь .bak, ошибка с понятным действием.
      Если миграция не нужна — пропустить этапы без лишнего ожидания.
- [ ] Тесты на отдельных копиях: обычный релиз, 28→31, отсутствие прав,
      недостаток места, повреждённый backup, активные клиенты, ошибка SQL,
