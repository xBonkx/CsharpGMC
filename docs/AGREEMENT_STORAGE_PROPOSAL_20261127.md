# AGR-10 — самостоятельный юридический договор: предложение модели

27.11.2026, Codex/main, исходный аудит `c6caa73`. Статус: PARTIAL,
проект решения для согласования. Миграция не реализована и не применена.
Рабочие базы, Cutover и резервные снимки в этом блоке не открывались.

## Почему требуется расширение

В текущем коде нет самостоятельного юридического договора:

| Данные | Текущее хранение/чтение | Ограничение |
|---|---|---|
| Объект строительства и общие реквизиты КС | `objects`, `SqlServerKsRequisites.Read/ReadShared` | Общие поля принадлежат объекту; разные договоры одного объекта не разделены |
| Номер/дата/наша организация | `contracts`, проекция `DocRow`, `AgreementPresentation.Resolve` | Получаются из приложений; до первого приложения источника нет |
| ДС | `contracts.kind=dop`, `base_contract_id` | Собственные номер/дата; основание может быть пустым/некорректным |
| КС-2 | `acts.contract_id`, строки актов | Привязка к существующему сметному документу |
| Общая КС-3 | `SqlServerKsContractScope` | Историческая группировка по эффективному номеру внутри объекта и группе актов |
| Подписанные файлы | Существующие привязки к `contract_id` | PDF сметного документа нельзя объявить общим PDF юридического договора |

Доказательства: `src/GmcSmeta.Core/Db/SqlServerWorkspace.AgreementCard.cs`,
`src/GmcSmeta.Core/Domain/AgreementPresentation.cs`, `AgreementAudit.cs`,
`src/GmcSmeta.Core/Db/SqlServerKsRequisites.cs`, текущий AGR TODO.
Это аудит исходников, а не фактической структуры/данных рабочего SQL Server.
`schema_reference.sql` — исторический ориентир, не готовый DDL для SQL Server.

## Предлагаемая модель

Сохранить `objects` как строительные объекты. Добавить `agreements`:
один объект может иметь несколько юридических договоров, каждый договор
может существовать без приложений. В дереве рабочее название берётся из
объекта; при нескольких договорах показывать отдельные договорные узлы
с номером/датой и явным состоянием незаполненных реквизитов.
Не объединять существующие карточки по совпадению названий.

| Новое поле/сущность | Предлагаемый SQL Server тип/правило |
|---|---|
| `agreements.id` | `bigint IDENTITY`, самостоятельный PK; старые ID не перенумеровывать |
| `agreements.object_id` | FK на `objects.id`, без каскадного удаления |
| `number`, `agreement_date` | `nvarchar(200)`, `date NULL`; черновик допускает пустые реквизиты |
| `company_id` | FK на существующий справочник наших организаций, точное имя/тип сверить с Pilot DDL |
| `subject`, `works_start`, `works_end` | `nvarchar(max)`, `date NULL`, `date NULL`; конец не раньше начала |
| Снимок заказчика/подписантов/печатных полей | Отдельные поля договора, включая адрес заказчика, `work_title`; полный перечень сверить с экспортами |
| `contracts.agreement_id` | Nullable FK; для приложения/ДС явная принадлежность по ID, КП остаётся самостоятельным |
| `contracts.annex_number` | Отдельный необязательный номер приложения; `name` остаётся его собственным названием |
| `agreement_files` | Собственная таблица привязок файлов к `agreement_id`, роль, исходное имя, адрес/хеш по принятому файловому механизму |
| `agreement_migration_map` | Журнал исходных ID, утверждённого сопоставления, версии/хеша плана; не источник юридических реквизитов |

Точные длины, nullable/default и FK-типы утверждать по SQL Server metadata
тестовой базы. Новую версию схемы пока не назначать: текущая обычная запись
ориентируется на 28, существует отдельный маршрут 28→31. Нельзя использовать
номер 31 повторно или менять release guard ради новой функции.

Не вводить UNIQUE по названию, номеру или набору номер/дата/подрядчик:
совпадение этих строк само по себе не доказывает юридическую идентичность.
Реквизиты контрагента — исторический снимок договора. Будущий CTR-справочник
обновляет его только явной командой с предпросмотром.

`contracts.number/date` в ходе перехода сохраняются без перезаписи.
Для `dop` это собственные реквизиты ДС; для старых `main` — исходные
договорные значения, оставленные для аудита/совместимости. Новый reader
явно различает юридический номер, номер приложения и номер ДС.
Новые реквизиты никогда не сохраняются в `objects.note/name`.

## Правила связей и наследования

1. Приложение выбирает `agreement_id` явно. Номер/дата основного договора,
   наша организация и общие печатные реквизиты читаются из договора.
   Создание нового договора не создаёт фиктивную смету.
2. ДС сохраняет собственные номер/дату. Имеет `agreement_id`; необязательная
   связь с приложением остаётся через `base_contract_id`. При наличии базы
   принадлежность договору и объекту должна совпадать. Прямое ДС к договору
   без приложения — отдельный новый сценарий, его включение требует решения.
3. Этап/остаток наследует договор от исходного документа; его нельзя
   автоматически интерпретировать как самостоятельный юридический договор.
4. Смену объекта/договора, копирование, импорт, КП→приложение, архив и корзину
   проверять в одной транзакции с действующими revision/ownership guards.
   Блокировать несовместимые связи, а не исправлять их молча.
5. Подписанный договор/PDF/КС и сохранённые исторические документы не
   перегенерировать. Изменение текущих реквизитов — явная операция;
   новые экспорты используют согласованный снимок, подписанные файлы неизменны.
6. КС-2 остаётся привязанной к `acts.contract_id`. Алгоритм общей КС-3 по
   effective number + object + группе актов пока сохраняется. Замена ключа
   на `agreement_id` — отдельное решение, включая аудит возможных объединений.
7. Reader печати возвращает отдельно реквизиты основного договора и ДС.
   Стандартные формы, ДНС, Р4, Excel/PDF проверяются по заполненным ячейкам
   и результатам экспорта, включая дату основного договора вместо даты ДС.
   Формулы, НДС, скидки и округление в этом блоке не менять.

## Сопоставление старых данных

Существующий `sql agreement-audit` — первый диагностический шаг, но не
разрешение на перенос. Он не доказывает единственность юридического договора.
На отдельно согласованной `GmcSmetaPilot_*` получить metadata и отчёт:
пустые номера/даты/организации, несколько номеров/дат/организаций на объект,
несвязанные/чужие базы ДС, этапы, КП, архивные/подписанные документы,
файлы, фактические группы КС-3. Дополнить проверкой потерянных FK.

Для каждого старого документа подготовить строку явного сопоставления:
старый ID, object_id, предполагаемый новый договор, основание выбора,
конфликты, решение владельца. Совпадающие реквизиты дают предложение,
а не автоматическое объединение. Разные договоры могут иметь одинаковые
номера; разные приложения могут содержать ошибки старого ввода.
Неоднозначные строки остаются несопоставленными, переход для них блокируется.
Пустые объекты сохраняются; договор для них создаётся по явному выбору.

## Последовательность будущей миграции

1. Утвердить эту модель, границы тестовой копии и явный mapping.
2. Подготовить отдельные версионированные SQL Server expand/backfill скрипты,
   проверки и маршрут release builder. Проверить исходную schema_version,
   реальные столбцы/FK/PK/defaults. Повторный запуск либо подтверждает тот же

3. На Pilot проверить COPY_ONLY/CHECKSUM backup, VERIFYONLY и реальный restore

4. До DDL записать counts, хеши старых колонок с разделением NULL/пусто,

5. В транзакции добавить таблицы/nullable связи, заполнить строго по
   утверждённому mapping, проверить принадлежность ДС/этапов, сохранить журнал

6. Сверить исходные хеши/ключи, финансовые отчёты, связи и файлы; при ошибке
   rollback, публикация запрещена. Затем прогнать CRUD/импорт/экспорт/архив/

7. Проверить старые клиенты: при несовместимой схеме запрет открытия/записи
   понятным сообщением. Не полагаться на их добросовестное поведение;
   остановка старых клиентов обязательна до переключения.
8. Отдельное согласование владельца перед любой рабочей миграцией.
   Релиз создаётся/публикуется только после проверок по SQL migration TODO.

## Обратимость и точки остановки

- До commit — обычный rollback транзакции. При сбое процесса после commit
  повторный запуск сверяет журнал и хеш плана; backfill повторно не выполняет.
- После commit, пока новые записи не появились, обратный скрипт на Pilot
  может снять только добавленные связи/объекты при точном совпадении журнала
  и неизменности старых данных. Это необходимо доказать отдельным тестом.
- После создания новых договоров/файлов/приложений простое DROP потеряет
  данные. Обратный переход блокируется; требуется новый согласованный план
  экспорта новых данных/восстановления и сверки. Автоматический RESTORE поверх
  рабочей базы запрещён. Backup остаётся отдельным аварийным вариантом.
- Не считать откат EXE откатом схемы. Старый клиент может не поддерживать
  новую схему; это отдельный критерий совместимости и остановки выпуска.
