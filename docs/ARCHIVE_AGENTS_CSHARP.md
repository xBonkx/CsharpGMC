# GMC-Смета C# — обязательные правила (checkpoint 7)

## Хранилище

- Единственный целевой СУБД для новой C#-версии: **Microsoft SQL Server**.
- **SQLite полностью исключена из новых сценариев C#, функций, тестов и миграций.**
- Старые классы `Microsoft.Data.Sqlite` в исторической части C#-ядра — только наследие незавершённого переноса. Не добавлять к ним возможности и не создавать fallback. Постепенно заменить SQL Server реализациями и удалить вместе с зависимостью при переносе оставшихся модулей.
- Python-версия и исходная SQLite-БД — архивный эталон поведения/форматов для сравнения, не целевой backend.

## Безопасность

- Никогда не подключать автоматические проверки к рабочему SQL Server: использовать только специально созданную `GmcSmetaPilot_*` базу.
- **Подтверждено пользователем 21.11.2026:** текущая локальная SQL Server база `GmcSmetaPilot_Cutover_20261120_160840` — **тестовая**, в ней разрешены INSERT/UPDATE/DELETE, проверки транзакций и откатов. Это **не** разрешение изменять другие БД, их резервные копии или производственный сервер; перед записью проверять фактические Server и Database строки подключения.
- Не менять исходные базы, эталон, опубликованное приложение и чужие несохранённые изменения. Изолированная копия проекта, отдельная тестовая БД и окно.
- Любое изменение нескольких записей — одна SQL-транзакция с предварительным сравнением `meta.rev`, проверкой принадлежности контракту и `locked`, журналом и новой ревизией после успеха.
- При удалении проверять любое использование позиции в КС-2, проведённых выдачах и закреплённых ведомостях. Не полагаться на `ON DELETE CASCADE` в тестовой SQL Server схеме: зависимые записи очищать явно и детей удалять первыми.
- Не обещать успешную сборку/тестирование на SQL Server без фактического запуска проверки.

## Обязательный визуальный паритет Python → WPF (с 21.11.2026)

- **Python 0.66.4 в `python/sql-server-current/smeta/ui/` — эталон внешнего вида и поведения.** Не придумывать новый дизайн и не ограничиваться подбором цветов по скриншоту.
- Для каждой переносимой страницы сначала читать её Python-реализацию, `theme.py`, источники размеров/столбцов/горячих клавиш. Переносить существующие отступы, типографику, пропорции, таблицу и состояние, адаптируя Qt к WPF. Единицы: Qt pt → WPF DIP с коэффициентом 4/3 для шрифта.
- Сравнивать Python и C# **на одном и том же договоре**, в одинаковом размере окна, масштабе и состоянии панелей. Разные договоры нельзя сравнивать по суммам, строкам и статусу.
- Общие визуальные ресурсы (`App.xaml`, `Theme/ToolbarIcons.xaml`) — единый источник оформления. Основные действия используют 18-DIP векторные иконки из Python theme.py, а не Unicode-псевдоиконки; активные подвкладки светлые, основные — синие. Не создавать новый локальный стиль, если существует общий; сохранять смысловые цвета и плотность таблиц.
- Приоритет: работающая таблица и операции, навигация по вкладкам, карточки итогов, затем визуальные тонкости. Никаких фальшивых кнопок или полей.
- Пользовательские настройки новой WPF сохранять отдельно в `%APPDATA%\\GMC-Smeta-Next`, не переписывать настройки установленного Python-клиента. Документ и денежные данные — только SQL Server.
- После каждого крупного блока — CI Windows build+offline tests и сверка интерфейса в Windows на тестовой базе. Указывать, какие проверки реально выполнены, а какие требуют локального запуска.

## Обязательная публикация изменений в main

- **После каждого завершённого и проверенного блока изменений самостоятельно выполнять commit и push непосредственно в `origin/main`** репозитория `xBonkx/CsharpGMC`. Не оставлять результат только локально, во временной ветке или в черновом PR, если пользователь прямо не попросил иное.
- Перед публикацией проверить `git status`, текущую ветку и актуальный `origin/main`; сохранить несвязанные/незакоммиченные изменения пользователя и других агентов, не делать `reset --hard` или `push --force`. При необходимости обновить ветку без потери чужой работы.
- Перед push выполнить доступные сборку и регрессионные тесты. При ошибках исправить их и повторить проверку; не объявлять блок готовым при упавшем CI.
- После push **проверить, что нужный SHA действительно находится в удалённой `main`**; дать пользователю SHA/ссылку на коммит и результат CI. Успех локального commit не означает, что push выполнен.
- Если прямой push в `main` не разрешён технически или защищён правилами репозитория, не обходить защиту: сообщить причину, сохранить проверенный результат в доступной ветке/PR (при возможности) и честно указать, что он ещё не в `main`.
- Обязательные архитектурные и безопасностные правила (SQL Server only, тестовая база, отсутствие изменений производственной БД) действуют и при срочных исправлениях.

## Обязательное непрерывное ведение единого реестра (25.11.2026, правило владельца)

- **Главный источник статусов — `csharp/docs/MASTER_TODO.md`.** Перед любым заданием (включая «продолжи», аудит, багфикс, рефакторинг, дизайн, оптимизацию, тестирование) проверить актуальный main, прочитать нужные строки реестра и исходный TODO. Не создавать независимые списки без регистрации ID в MASTER_TODO.
- До реализации зафиксировать взятые ID, агент/ветку/дату (IN PROGRESS); не брать чужие активные задачи без согласования. Новое замечание получает устойчивый уникальный ID, приоритет, источник/файлы, критерий приёмки; дубли связывать с каноническим ID, не удалять историю. Исходные подробные аудиты сохранять.
- **Каждый блок изменений = код/тесты + актуализация MASTER_TODO, соответствующего исходного TODO и CURRENT_TASK в том же коммите.** По каждому затронутому ID записать статус, что именно сделано, доказательство (коммит/файл/тест, дата и фактический результат), конкретный остаток/блокер, следующий шаг. Если блок ничего не закрывает, зафиксировать PARTIAL или BLOCKED; не отмечать все задачи блока одним общим DONE. Для нового коммита допустима ссылка на изменённый файл/тест; после публикации подтверждать SHA. Обновлять связанные Issues и ROADMAP, если затронут их объём; не дублировать задачи.
- Статусы: UNVERIFIED (не выяснено), NOT STARTED (проверено отсутствие реализации), IN PROGRESS, PARTIAL, CODE READY (код готов, приёмка открыта), DONE (все необходимые проверки фактически пройдены), BLOCKED (причина), DUPLICATE (канонический ID), N/A (обоснованное согласованное исключение). Чекбокс закрывать только при DONE. Не выдавать статическую проверку за сборку, запуск тестов, GUI, SQL Pilot или замеры. При регрессии переоткрывать ID.
- После каждого блока пересчитать сводку по статусам и по спискам, отдельно число оставшихся кодовых правок, задач приёмки и неизвестных статусов; не считать окна/Issues/ROADMAP вторично. Проверить уникальность ID, сумму строк и статусов, ссылки, сохранение чужих изменений. При параллельных изменениях main перечитать свежий реестр и объединить строки, не перетирать чужие статусы и не использовать force push.
- Перед публикацией выполнить доступные проверки и честно указать невыполненные; после push проверить удалённый main и сообщить SHA, IDs, число полностью закрытых, частичных, ожидающих приёмки и остаток. Если доступ к Windows/SQL отсутствует, это не основание ставить DONE. Рабочую БД не трогать.
- Эти требования распространяются на все чаты и агентов проекта и имеют приоритет над старой формулировкой «Статус → DONE» после любого блока. Вести реестр постоянно, а не только при очередном аудите.
