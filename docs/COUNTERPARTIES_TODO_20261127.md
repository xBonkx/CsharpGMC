## 1. Цель и существующие данные

Один раз завести организацию, затем выбирать её при создании договора/КП, закупке, письме или исполнительном документе. Не вводить ИНН, адрес и подписантов повторно. Один контрагент может выступать в разных ролях: заказчик, генподрядчик, техзаказчик, поставщик, субподрядчик, прочее.

Статическая сверка исходников:
- `SchemaData.cs`: уже есть `companies` (наши организации), `suppliers`, `contracts.company_id`, `procurement.supplier_id`, текстовые поля заказчика и подписантов в карточке. Не смешивать наши организации с внешними.
- `SqlServerProcurement.cs`: закупки связываются с `suppliers`, умеют найти/создать поставщика по имени; «Цех» имеет специальную семантику источника закупки. Не заменять этот механизм одномоментно.
- `SqlServerKsRequisites.cs`, `SqlServerWorkspace.AgreementCard.cs`, `AgreementCardView.xaml(.cs)`: общие печатные реквизиты хранятся на уровне карточки, индивидуальная часть стройки — на уровне сметного документа.
- `SqlServerLetters.cs`: получатель хранится текстом, письмо имеет payload_json. Сохранить исторические значения.
- `MainWindow.Navigation.cs`, `WorkspaceReferenceWindows.cs`: существующая команда «Наши организации» и паттерн справочников.
Содержимое реальных БД не проверено; описание схемы — исходники, а не утверждение о действующем SQL-сервере.

Открывать в основной рабочей области, с кнопкой возврата; существующие цвета, шрифты, таблицы и стили WPF. Новые иконки не придумывать, соблюдать AGENTS.md.

## 3. Карточка контрагента

- Основное: короткое и юридическое имя, вид (юрлицо/ИП/прочее), ИНН, КПП (если применим), ОГРН/ОГРНИП, юридический и фактический адрес, сайт, примечание, роли, активен/архив.
- Контакты: несколько лиц (ФИО, должность/роль, телефон, email, примечание). Выбор основного контакта и подписанта по назначению; руководитель и подписант могут отличаться. Основание полномочий — опциональное поле. Не хранить паспортные данные.
- Банк (вторая очередь): несколько счетов, банк, БИК, расчётный/корреспондентский счёт, отметка основного. Не хранить пароли и банковские доступы; права и аудит согласовать.
- История: связанные карточки договоров и КП, приложения/ДС, переход к документам. Закупки — заказы/поставки по подтверждённым связям. Суммы договоров, закрыто по КС и остатки — только из существующих авторитетных расчётов, без дублей и смешивания подписанного/неподписанного. Сумма закупок не равна оплате.
- В дальнейшем возможны приложенные файлы карточки, если согласована модель хранения и доступ; не обязательны для первой версии.

ИНН и банковские идентификаторы — строки, ведущие нули не терять. Проверять формат ИНН и контрольную сумму для поддерживаемых российских типов; не запрещать иностранного контрагента без ИНН. Предупреждать о совпадениях ИНН+КПП, названия/алиасов; не сливать автоматически одноимённые организации и разные КПП. Архив вместо физического удаления связанных записей.

## 4. Интеграции

### Договор и КП (первая очередь)

В `AgreementCardView` добавить поиск/выбор заказчика из справочника, создание новой карточки контрагента, просмотр выбранного и явную команду «Подставить реквизиты». Для нового договора/КП допускается предварительное заполнение с возможностью проверки. У существующего договора при замене показать какие значения изменятся (короткое и полное название, адрес, организация/должность/ФИО подписанта), применить только после подтверждения. Стройка, название договора, номер, дата, сумма, НДС, наш подрядчик и локальные реквизиты приложений не изменяются от выбора заказчика. Предусмотреть второго участника отдельной ролью, не копировать автоматически руководителя вместо подписанта.

### Двусторонний обмен договор ↔ справочник (обязательно в первой очереди CTR-03)

Уточнение владельца 27.11.2026: справочник не должен быть отдельной обязательной точкой ввода. Контрагента можно завести непосредственно из договора, и наоборот — импортировать (подставить) его реквизиты из справочника в договор. Ручное заполнение договора без связи сохраняется.

В разделе реквизитов договора/КП, рядом с заказчиком (и отдельно для второго участника):
- «Выбрать из справочника» — поиск по названию/ИНН, выбор существующего контрагента, контакта/подписанта и подходящей роли. Предпросмотр заполняемых полей, затем подстановка в текущий договор и сохранение связи.
- «Добавить в справочник» — открыть заполненную черновую карточку на основании уже введённых реквизитов договора, без повторного ввода. Недостающие ИНН/КПП и прочие поля можно дополнить. Проверить дубликаты до создания, предложить привязать существующего; не требовать сначала закрыть договор и зайти в главное меню. После сохранения связать текущий договор с выбранной/созданной карточкой, сохраняя введённые договорные реквизиты.
- «Обновить контрагента из договора» — для уже связанного контрагента сравнить данные по полям, явно выбрать переносимые изменения и подтвердить. Пустое поле договора по умолчанию не стирает заполненное поле справочника; очистка только отдельным осознанным выбором.
- «Обновить реквизиты договора из справочника» — обратный перенос актуальных значений в выбранный договор с таким же сравнением и подтверждением. Не затрагивать другие договоры.
- «Открыть карточку контрагента» — переход к данным и истории без потери несохранённых правок; из вкладки «Договоры» контрагента — обратный переход в конкретный договор.

Обмен по стабильному ID и роли, не по совпадению имени. Сравнение показывает источник, старое и новое значение, отметки переноса. Копировать только соответствующие полям организации и подписанта значения; не извлекать автоматически ИНН/адрес/ФИО из произвольного текста без подтверждения, не копировать реквизиты стройки, наши организации, договорные суммы, номера, НДС, банковские данные без явного выбора. При неполных реквизитах допускается черновая карточка без выдуманных значений. Отмена не создаёт и не изменяет записей. Согласованное создание/привязка или обновление с сохранением договора выполняются атомарно либо через явно разделённые подтверждённые операции с обработкой конфликта ревизий; не оставлять незаметные частичные записи и не затирать чужие правки.

Это двусторонняя подстановка по команде пользователя, а не фоновая синхронизация. Изменение справочника не переписывает старые договоры, а изменение договора не переписывает другие договоры или справочник автоматически. Исторические снимки и подписанные файлы сохраняются.

### КС-2/КС-3 и документы

Справочник — источник заполнения, а не динамическая замена всех исторических реквизитов. Договор сохраняет согласованный набор печатных данных (снимок) в существующих полях; экспорт берёт его, а не «самую свежую» карточку контрагента. При обновлении адреса/ФИО в справочнике старые договоры не изменяются; можно явно обновить данные конкретного договора после сравнения. Подписанные PDF и закрытые документы не перезаписывать. Существующую группировку КС, расчёты и индивидуальные части объекта не менять. Исторический экспорт подписанных актов требует отдельной проверки правил фиксации реквизитов; не обещать неизменность повторной выгрузки там, где снимок акта ещё не реализован.

### Закупки (вторая очередь)

Сохранить supplier_id и существующие истории; предложить связь старой записи suppliers с контрагентом. Использовать выбор по ID, не по имени. Существующие поставщики без связи продолжают работать, можно завести/сопоставить вручную. «Цех», внутренние перемещения, статусы, расчёты закупки и остатки не менять. Опционально автоподстановка контакта в заявку, без автоматического изменения старых счетов и заказов.

### ПТО, письма, АОСР, приказы (третья очередь)

Выбор получателя/участника из справочника с явным заполнением поля в текущем документе. Сохранение копии реквизитов в документе, старые письма и шаблоны не переписывать. Технический заказчик/генподрядчик и ответственное лицо — разные роли, не считать их одним человеком.

## 5. Предлагаемая модель SQL Server (только для согласования)

Новая внешняя сущность, условно counterparties, contact/person и bank accounts, таблица ролей либо другой нормализованный механизм. Связь карточки договора с контрагентами по ролям и стабильным ID; привязка поставщиков через nullable ID или отдельную таблицу сопоставления. Точные таблицы/ключи/индексы утверждать после аудита AGR-01/10 и SQL-совместимости: карточка objects не всегда равна одному юридическому договору. Не связывать неоднозначные старые группы автоматически. Не переименовывать objects/contracts/company_id/supplier_id, не вводить вторую систему расчётов. Сохранить текстовые реквизиты и работоспособность старых записей без связи. Индексы по нормализованному имени/ИНН, внешний ключ с запретом каскадного удаления истории; дубликаты с одинаковым ИНН/разным КПП допустимы. Точные ограничения уточнить при реализации.

Миграция только по отдельному согласованию владельца, после резервной копии на GmcSmetaPilot_*. Идемпотентность, обратимость, проверка версии схемы и совместимости Python/C#; блокировка production и Cutover, не расширять допуск записи. Не менять текущую схему 31 и release guard в рамках этого ТЗ. Автосопоставление только как список предложений, подтверждение человеком; исходные строки не удалять. Запись в транзакции с meta.rev и журналом, права доступа и конфликт двух сотрудников. Внешний поиск по ИНН/ЕГРЮЛ — опциональная отдельная задача, без сетевой зависимости и платного API по умолчанию.
