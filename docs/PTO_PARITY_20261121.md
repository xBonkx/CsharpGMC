## Схема SQL

- gmc_pto_packages: сериализованный снимок АОСР с объектом/договором, номером, статусом и revision. Встроенные JSON-массивы: приложения, исходные работы, выбранные системы, снимки сертификатов, вручную заданный порядок.
- gmc_pto_history: каждое подтверждённое изменение/удаление.
- gmc_pto_certificates: глобальная библиотека подтверждающих PDF, SHA и revision.
- gmc_pto_object_profiles: проектная/подписная заготовка на объект, не меняет базовые объекты.
- gmc_pto_releases: история каталогов выпусков, контрольный SHA описи.

Отчётный номер уникален в пределах object_id по SQL индексу, с сериализуемой транзакцией, SQL sp_getapplock и контролем ревизии. Конкурентная запись не перетирает другой клиент. Ни одна операция ПТО не делает UPDATE финансовых таблиц.

## Файловые архивы

Оригиналы вложений копируются под UUID-именами в files/ и сохраняют SHA. Пользовательский общий каталог выбирается отдельно; для нескольких компьютеров необходимо одно защищённое сетевое хранилище с одними путями и SMB ACL. Исключённые документы не попадают в реестры и сборку, но оригиналы не уничтожаются.

Выпуск составляется в отдельной временной папке и публикуется переносом только после проверок всех файлов. Состав: АОСР XLSX, общий реестр XLSX, перечень исполнительных схем, реестр сертификатов и паспортов, перечень документов для сдачи, реестр качества при более пяти включённых документах, все включённые оригиналы, объединённый PDF документов о качестве (если есть) с закладками и JSON-опись с SHA каждого файла. Копии не сохраняют электронные подписи оригинальных PDF.

ZIP v2 содержит JSON из SQL Server, файлы, пользовательские шаблоны и выпуски. Восстановление допускается исключительно в пустые таблицы ПТО базы GmcSmetaPilot_* и новую пустую папку, с проверкой путей/ссылок/размера и SHA до SQL-коммита. Объекты с исходными object_id должны уже существовать в целевой пилотной SQL базе.

## Ограничения и приёмка

- Встроенный режим ПТО — локальный UI-переключатель, как в Python, а не замена разрешения SQL Server. Реальное разделение полномочий обеспечивается отдельным логином/ролями SQL и SMB ACL. Автоматическое серверное разграничение прав ПТО в этой ветке не введено.
- Общее редактирование основных реквизитов объекта остаётся в штатной карточке объекта; окно ПТО изменяет только свои заготовки. Уже выпущенные акты не переписываются после исправления объекта.
- В отличие от Python, сертификат проверяется по файлу при загрузке; страницы PDF не угадываются. Применимость материалов, полномочия подписантов, содержание схем остаются только для ручной проверки.
- История выпусков хранится в SQL, требуется доработать отдельное удобное окно просмотра выпусков и ручную проверку восстановления из реального архива.
- Отдельный офлайн-импорт из исторического pto.sqlite3 пока не реализован. SQLite никогда не должен становиться runtime backend C#.
- Проверка ZIP подтверждает защиту от ../, дублированных имён и symlink в автоматизированном Windows-тесте; фактическое ZIP+SQL-восстановление в файловую папку на SMB остаётся ручной приёмкой.
- Не выполнен ручной UI тест на одном пилотном объекте при 1920x1080 и 1366x768, реальные шаблоны/печать в Microsoft Excel, SMB, сквозное добавление ВОР из КС и подписи. Статус полной production-приёмки остаётся открытым.
- Автоматические тесты: PtoRulesTests, GmcSmeta.Pto.Checks, GmcSmeta.Pto.SqlChecks; Windows/SQL workflow: .github/workflows/pto-parity.yml. Цифры указывать только по завершённым CI.
- PR не сливать самостоятельно: координатор выполняет интеграцию в main. Рабочую базу не изменять.
