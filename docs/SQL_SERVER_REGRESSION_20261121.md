# Регрессионная проверка SQL Server — блок 14 (21.11.2026)

Область: **только SQL Server**. В целевой C#-версии SQLite не используется. Локальная «рабочая» база пользователя сейчас является **тестовой копией**, но эта сессия не имеет к ней сетевого доступа. Тесты выполняет Windows после `git pull`.

## Сборка и тесты

1. Закрой все окна `GMC-Smeta-Next.exe`, иначе DLL будет заблокирована (MSB3021 / MSB3027).
2. В корне репозитория:
   ```powershell
   dotnet build csharp/GmcSmeta.slnx --no-restore
   dotnet test csharp/tests/GmcSmeta.Core.Tests/GmcSmeta.Core.Tests.csproj --no-restore
   ```
3. Убедись, что окружение `GMC_SMETA_SQL_CONNECTION` указывает на **копию**. Текущий защитный механизм записи требует имя базы с префиксом `GmcSmetaPilot_`. Нельзя обходить его переключением на производственную БД.

## «Закупки» — ручная проверка

- Открой договор → Закупки. Не должно быть `InvalidCastException` (поле `direct_to_site` — это SQL `bit`, не имя поставщика).
- Проверь, что названия поставщиков, примечания и флаг «прямо на объект» не перепутаны.
- У позиции с поставщиком измени только этап на «Оплачено». После повторного открытия проверь: этап сохранён кодом `paid`, поставщик прежний.
- Измени закупочную цену, затем очисти её; в базе `procurement.cost_price` должно стать `NULL`. Аналогично проверь очистку срока `due_date`.
- Проверь поиск, фильтр «В работе» и «Без закупочной цены», а также сохранение статуса операции внизу окна.
- Импортируй XLSX с двумя одинаковыми наименованиями и ед. измерения, но разными заявками. Данные должны попадать **разным позициям**, если соответствующие дубликаты существуют в смете. При создании новой записи закупки не должно быть ошибки nullable id.
- В импортируемом XLSX этап «Оплачено» должен стать `paid`, «Счёт» — `invoice`. Неизвестный этап должен выдавать понятную ошибку и откатывать транзакцию.
- Проверь движения и выдачу через ведомость на тестовых позициях.

Для сверки в SQL Server на **копии** можно выполнить SELECT (без изменений):
```sql
SELECT TOP (100) p.id, p.name, pr.stage, pr.cost_price, pr.due_date,
       pr.direct_to_site, pr.note, sup.name AS supplier
FROM dbo.positions AS p
LEFT JOIN dbo.procurement AS pr ON pr.position_id = p.id
LEFT JOIN dbo.suppliers AS sup ON sup.id = pr.supplier_id
ORDER BY p.id;
```

## «Сводная» — ручная проверка

- Для позиции без фактического `procurement.cost_price`, но с плановым `positions.purchase_price`, себестоимость должна использовать **план**.
- После внесения фактического закупа должна использоваться **фактическая** цена. Значение `0` — отдельная заданная цена, не пропуск.
- Закуп комплектующих суммируется с родительской позицией ровно один раз; итог карточек = сумма позиций + доп. расходы.
- На смете с 2500+ строками проверь загрузку и фильтры «Сводной».
- У **подписанного договора** редактор себестоимости только для чтения: наценка СМР и редактирование итоговых сумм запрещены.
- На разблокированном документе доступна кнопка «Наценка на СМР…». Проверяй её только в тестовой копии.

Ожидается: значения C# совпадают с Python для **одного и того же документа**; на снимках разных документов цифры сравнивать некорректно.

## Блок 15 — КС-2, КС-3 и выдача (21.11.2026)

Перед тестами закрой `GMC-Smeta-Next.exe`, проверь подключение
`GMC_SMETA_SQL_CONNECTION` к копии `GmcSmetaPilot_*`.
Сборка:
```powershell
dotnet build csharp/GmcSmeta.slnx
dotnet test csharp/tests/GmcSmeta.Core.Tests/GmcSmeta.Core.Tests.csproj
```

Проверка КС-2:
1. Открой договор → «КС-2 / КС-3» → создай новый акт; после
   создания редактирование должно работать без NullReferenceException
   или ошибки Transaction required.
2. При КП 10 шт., уже закрытых 4 шт. другим актом, текущему доступно
   не более 6 шт. Ввод 7 отклоняется, 6 разрешён.
3. Введи `К2*1,5` в строку, которая имеет ссылку на видимый номер К2.
   Формула принимается и остаётся привязанной к стабильному ID.
4. «Заполнить из сметы» НЕ создаёт строк вне КП по 1 шт. Автоматически
   закрывает только позиции с ненулевым остатком. При ошибке в середине
   пачки ни одна строка не должна записаться.
5. «Очистить акт» требует подтверждения и откатывается целиком,
   если одна позиция недоступна.
6. После подписи акта редактирование количества заблокировано.

Проверка КС-3:
1. «КС-3» открывает расчётную ведомость с суммами за период,
   год, с начала работ; сравни цифры с Python на том же акте.
2. Нажми «Сохранить Excel» — суммы должны оказаться числовыми
   ячейками, предыдущие акты включены.
3. Это расчёт, НЕ официальный печатный бланк КС-3.

Проверка выдачи:
1. Создай новую ведомость; повторно открой/измени количество:
   не должно быть ошибок null Revision или nested DataReader.
2. «Добавить строки» — Ctrl+щёлчок или Shift выбирают несколько;
   ранее добавленные позиции и подстроки-комплектующие не предлагаются.
3. Количество не должно превышать остаток по объекту/позиции;
   редактирование позиции другого объекта отклоняется SQL Server.
4. Проведи ведомость: в движениях появляется «out» по строкам.
   Сними фиксацию: движения должны исчезнуть; повторная фиксация
   не создаёт дубликатов. Убедись, что при ошибке сообщение остаётся
   видимым и отметка возвращается к состоянию БД.
5. Проверь повторный экспорт и суммы в Excel после изменений.

Контроль: никакого SQLite в новых тестах; DB-операции выполняются
только на разрешённой SQL Server копии. При ошибке после сборки
скопируй первое `error CS...` или `error MC...` полностью.

## Блок №16 — встроенная КС, навигация и реквизиты

1. Открой договор → «КС-2 / КС-3». Теперь страница не должна
   создавать отдельное окно: внутри основной панели видны
   «Акты (КС-2, КС-3)» и «Сводная по выполнению».
2. Слева должны быть группы КС-3 (например, КС-2 8.1 + 8.2 под
   КС-3 8) с суммами и поиском. Фильтры «Черновики»/«Подписанные»
   должны показывать только подходящие акты, не менять общий итог.
3. Выдели/открой КС-2 двойным щелчком: полноценный редактор
   остаётся **внутри договора**. Попробуй «← К списку актов»,
   «Заполнить из сметы», подпись и расчёт КС-3.
4. Открой «Сводная по выполнению»: отдельные колонки по каждому
   акту, «По КП», «Закрыто всего», «Подписано», «Остаток»,
   «Остаток, ₽», «Выдано», поиск и фильтр остатка.
   Для 2500+ строк проверь плавность скроллинга.
5. Экспорт «Сводной по выполнению» в Excel: суммы и объёмы
   должны быть числовыми ячейками. Учитывай, что «Остаток, ₽»
   пока не включает отдельную сумму СМР/транспорт/ПНР.
6. «Реквизиты для КС…»: заполни заказчика, часть объекта,
   подписантов, вид работ. Сохрани, закрой, снова открой,
   проверь сохранение в копии SQL Server.
7. Вернись на «Смету» в том же договоре: кнопки, таблица и
   нижние итоги должны вернуться без потери состояния.
8. В CI должны пройти `dotnet build` и тесты KsWorkspaceProjection;
   проверка с конкретными договорами требует локального SQL Server.

Честно ещё отсутствует: общая КС-3 группы нескольких ДС,
официальные формы экспорта и полноценная Python-логика СМР
по актам. Это не заглушки: отсутствующие функции не объявляем
готовыми.
