## Архитектура SQL

Изолированные таблицы:

- `dbo.gmc_metal_materials` — уникальная категория+наименование;
- `dbo.gmc_metal_movements` — append-only журнал с идентификатором операции, м²×1000 (BIGINT), шт., резервом, отправителем/получателем, объектом, работником, партией, примечанием;
- `dbo.gmc_metal_lots` — партии, поставщик/счёт и исходная площадь/количество;
- `dbo.gmc_metal_opening` — однократный первоначальный импорт, SHA256 исходной книги;
- `dbo.gmc_metal_register` — общая исходная XLSX-книга с ревизией;
- `dbo.gmc_metal_register_history` — версии/sha256/сотрудник.

DDL выполняется только после двух проверок: **имя каталога строки подключения** и **фактический `SqlConnection.Database`** начинаются с `GmcSmetaPilot_`. Складская запись — `SERIALIZABLE` и `sp_getapplock`, затем проверка `meta.rev`, запись движения и bump ревизии в одной транзакции. Одновременные операции через одно и то же приложение сериализуются; допустимое количество проверяется внутри транзакции. Уникальный `operation_id` препятствует повторному проведению того же идентификатора. При SQL-ошибке транзакция откатывается без частичного результата.

**Источник правды:** складское движение; не смешивать физический остаток, остаток у поставщика, потребность объекта, выданное и резерв. Не редактировать прошлые движения непосредственно в SQL. Для исправлений предусмотрена `Корректировка` с обязательной причиной; сторнирование других типов как отдельная команда **не реализовано**.

## Как работать

1. Открыть **Меню → Учёт металла**; загрузить исходную XLSX, отредактировать в таблице, **Сохранить для всех**. При конфликте сохранения локальные изменения остаются в редакторе — их можно **Выгрузить Excel** и затем обновить.
2. В **Меню → Склад металла** выполнить **Перенести остатки из Excel**, ознакомиться с расхождениями и подтвердить **однократный** импорт. Не импортировать просто ради проверки: использовать отдельную тестовую `GmcSmetaPilot_*`.
3. Оформлять потребности и резерв под конкретные объекты; выдавать из **физических** мест хранения. У поставщика материал находится отдельно до регистрации оплаты и получения партии.
4. Новую партию сначала добавляют, затем отмечают оплату, затем оформляют её **получение** в реальное место хранения. Частичное получение допустимо при условии, что количество бухт и площадь партии завершаются одновременно.
5. Сверять по вкладкам «Остатки», «По объектам», «Операции», «Закупки и хранение»; выгрузить XLSX через «Отчёт Excel…».

## Ограничения / открытые проверки

- Нет доступа к живому изолированному SQL Server внутри этого удалённого сеанса: не проведены SQL-интеграция, два параллельных клиента, откат при реальном исключении, проверка реального `MERGE`/индексов, сетевые задержки и миграция на фактических книгах.
- Исторический Python исходный склад работал с `dbo.metal_entries`; новая C# модель физически отделена. **Автоматический перенос существующих строк журнала Python/SQL в новые таблицы пока не реализован.** Начальный XLSX импорт один раз, а не миграция уже проведённых операций; повторно вводить действующие движения нельзя.
- Общий редактор XLSX поддерживает обычные ячейки, объединённые области и безопасные формулы `SUM(A1:B2)`, ссылки и базовые операторы; макросы, внешние ссылки, новые формулы, массивы, сложные функции Excel не поддерживаются. Исходная Python модель также отвергает многие сложные функции.
- В `ReadSnapshot` используются SQL-агрегаты; их необходимо сравнить со специфическими историческими случаями Python, включая старые отрицательные потребности, ручные корректировки и унаследованные «у поставщика».
- Ключи `objects.id` в складском журнале не имеют внешнего ключа из-за сохранения исторических движений: интеграцию удаления/переименования объектов C# с новым журналом нужно проверить отдельно.
- Перед слиянием необходимы Windows GUI smoke-test, визуальная сверка с Python, `GmcSmetaPilot_*` с тестовой книгой, строгая двухклиентская конкурентная выдача, повтор импорта и экспорт/перезапуск.
- Пилотные блокировки **не удалять** в этой задаче. Производственная база недоступна.
