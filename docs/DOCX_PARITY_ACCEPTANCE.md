## Confirmed OOXML/file-publication gap and isolated implementation

Existing `PeopleDocuments.FillDocx` writes directly to `FileMode.CreateNew`; an exception during replacement (e.g. unknown placeholder) can leave a partially written output. Also, `UniquePath` checks an available filename before creation and cannot reserve it across two clients. Neither is an SQL-state issue, but both matter for archival safety.

New **`DocxTemplateParity`** is an *optional* adapter over the existing generator, not a second template engine:
- validate DOCX ZIP integrity and essential OOXML parts, reject traversal and duplicate entry names (case insensitive);
- inspect document, table paragraphs, headers and footers for unresolved placeholders after replacement, including split Word text runs;
- generate to random private staging in the chosen directory and then publish via same-directory `File.Move`, with no overwrite and collision suffixes `(2)`, `(3)`…;
- remove staging on failure; never modify input template, real archives or SQL.
- **No new OrdersWindow hook in this PR**. Wiring this adapter to the real issue/registration flow must be agreed with the Orders owner/coordinator; new tests exercise the adapter directly.

This does not assert that arbitrary external Word templates, content controls, complex field codes, macros, charts, embedded OLE, cryptographic signatures, tracked changes, footnotes, or unusual XML namespace prefixes are supported. The existing template engine uses `<w:t>` replacement within `<w:p>`. Such cases require a real original template and separate validation.
