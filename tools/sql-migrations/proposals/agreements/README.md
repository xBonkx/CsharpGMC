Исходники из этой папки использует `GmcSmeta.AgreementMigration` после отдельного
разрешения владельца. Режим rehearsal действительно восстанавливает backup,
проверяет пустой и принудительный транзакционный откат и неизменность исходника.
Режим apply-office допускает только DIMA\SQLEXPRESS/GmcSmetaPilot_Cutover_20261125,
требует успешный отчёт и неизменность данных с rehearsal, backup+VERIFYONLY,
SINGLE_USER WITH NO_WAIT, единую транзакцию DDL/backfill/хеш-проверок и возврат
MULTI_USER. Рабочая схема уже 32. Текущий установленный 1.0.6 ждёт нового релиза.

автоматический destructive downgrade/RESTORE поверх рабочей базы не выполняется.

# AGR-10: скрипты для отдельного согласования, НЕ текущий маршрут выпуска

Статус 27.11.2026: подготовлены исходники SQL Server, не выполнялись.
Схема 32 — предложенный номер. `SqlMigrationPlan`, `approved-schema.txt`,
production guards и клиенты не изменены; текущий EXE новую схему не открывает.
Эти файлы не копируются автоматически в выпуск и не запускаются приложением.

- `expand_v32.sql` добавляет самостоятельные договоры, связи приложений,
  собственные файлы и журнал будущего утверждённого сопоставления.
  Старые ID, number/date, суммы, акты и файлы не переписываются.
- `rollback_empty_v32.sql` отменяет только пустое расширение. При наличии
  новых данных/связей останавливается; DROP с потерей записей не допускается.
- Скрипты требуют точно названную отдельную `GmcSmetaPilot_Test_Agreement_*`,
  дополнительный session context с её точным именем, отсутствие других клиентов,
  ожидаемую схему/типы ключей и эксклюзивную серверную блокировку.
  Эти проверки не заменяют отдельное согласование владельца и резервную копию.

Перед первой SQL-проверкой нужны отдельное разрешение владельца и создание
синтетической Pilot-копии. До DDL: COPY_ONLY/CHECKSUM backup, VERIFYONLY,
реальный restore, сверка исходных хешей/ключей/сумм и исключение записи клиентов.
Реализацию/приёмку этого runner нельзя подменять ручным выставлением context.

Тестовый сценарий после разрешения: чистая 31 → expand → повторный expand;
проверка PK/FK/defaults и сохранности старых колонок; создание пустого договора;
проверка запрета чужого object_id и неверных сроков; запрет rollback с данными;
на отдельной пустой копии expand→rollback, сравнение старых данных; отказ для
другого имени, Cutover, чужого клиента, несовместимых типов/версии, ошибка/rollback.

Не подготовлены и не выполнялись backfill реальных документов и production
cutover: без аудита разрешённой копии нет утверждённого mapping. Совпадение
названий/номеров не является таким mapping. Предварительный аудит уже доступен
в `sql agreement-audit`, но не даёт разрешения автоматически объединять записи.
