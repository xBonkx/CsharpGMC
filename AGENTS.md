# GMC-Смета — обязательные правила для всех агентов

До любого блока работ (включая «продолжи») сверить свежий main и [MASTER_TODO](docs/MASTER_TODO.md), [CURRENT_TASK](CURRENT_TASK.md). Сначала текущий приоритет владельца: [Python 0.66.4–0.67.9](docs/PYTHON_0664_TO_0679_PARITY.md) и [SQL migration/release](docs/SQL_MIGRATION_RELEASE_TODO.md). Архивные задачи не терять, но не переключать на них текущий приоритет без решения владельца.

- Полные исходные аудиты сохранены в docs/: UI_VISUAL_TODO, PERFORMANCE_TODO, CONTEXT_MENU_TODO, FUNCTIONAL_BUG_TODO, SMALL_TASKS, ROADMAP, профильные acceptance/parity документы. Открытые архивные Issues — [ARCHIVE_OPEN_ISSUES](docs/ARCHIVE_OPEN_ISSUES.md). 400 архивных ID не означают 400 новых ошибок; сверять код и критерии, исключать дубли только с каноническим ID. Старые пути csharp/src и csharp/tests теперь src и tests; Python-эталон читать в xBonkx/gmcsmeta и архиве, не менять.
- Перед работой фиксировать ID, агент/ветка/дата, не брать занятые задачи. Новые задачи регистрировать в MASTER_TODO. Каждый блок = код/тесты + обновление MASTER_TODO, соответствующего исходного TODO и CURRENT_TASK в том же коммите. Указывать фактические проверки, доказательства, остаток, SHA/путь и дату. Статусы UNVERIFIED, NOT STARTED, IN PROGRESS, PARTIAL, CODE READY, DONE, BLOCKED, DUPLICATE, N/A. DONE только после реальной приёмки; не путать статическую сверку, сборку, тесты, GUI, SQL и измерения. При регрессии переоткрывать. Пересчитывать сводку, не суммировать окна/Issues/ROADMAP повторно.
- Не трогать рабочую БД. Только явные отдельные тестовые копии; схема 31 и production guard остаются заблокированными до согласованной приёмки. Сохранять чужие изменения, не применять force push. Не публиковать релиз без проверок. Сборка: dotnet build GmcSmeta.slnx; тесты: dotnet test GmcSmeta.slnx. Для UI/SQL/экспорта проверять соответствующие acceptance-критерии, включая 2500+ строк и два клиента. Не утверждать прохождение без запуска.
- Исторические подробные правила: [корневой AGENTS](docs/ARCHIVE_AGENTS_ROOT.md), [C# AGENTS](docs/ARCHIVE_AGENTS_CSHARP.md). При расхождении приоритет у текущего владельца и настоящего файла.

- По прямому указанию владельца от 25.11.2026 согласованные точечные правки коммитить непосредственно в свежий `main` (без force push, не затирать параллельные изменения). Обновлять TODO в том же коммите; не считать merge приёмкой и не публиковать релиз без проверок.

- По указанию владельца от 26.11.2026 каждый готовый коммит сразу отправлять в `origin/main`. Перед push сверять свежий main, учитывать чужие изменения и не использовать force push. Push кода и публикация релиза выполняются отдельно.

- **Обязательный точный паритет иконок (владелец, 25.11.2026):** источник — свежий `xBonkx/gmcsmeta`, прежде всего `smeta/ui/theme.py` (_P/icon) и фактический вызов icon(...) в соответствующем Python-экране. Запрещены подбор «по аналогии», внешние наборы и самодельная замена. Сохранять имя, исходную SVG-геометрию, viewBox, stroke, размер, цвет и состояния; преобразование SVG в WPF допустимо только эквивалентное (включая circle/rect/ellipse). Если у исходной команды иконки нет, не добавлять её. Для C#-only команд, не имеющих аналога, явно указать это и не выдавать выбор существующего SVG за доказанный паритет; новые иконки согласовать. Для каждого UI-блока записать SHA Python, файл/вызов, соответствие ресурса; проверить исходники и отдельно рендер при DPI, без утверждения визуального совпадения по одному имени. В отчёте владельцу приводить фактические git diff additions/deletions отдельно для приложения, тестов и документации, число файлов и SHA.

- **Размер файлов и декомпозиция (владелец, 26.11.2026):** для рукописных `.cs` и `.xaml` считать физические строки (включая пустые и комментарии): до 500 — цель; 501–1000 — допустимо; 1001–1500 — проверить ответственность; 1501–2000 — кандидат на выделение компонентов; 2001–4000 — приоритетный рефакторинг; >4000 — не допускать без явного согласования владельца и записанного обоснования. Перед изменением оценить размер и связность; новую независимую функциональность не добавлять в уже раздутый класс, если можно выделить компонент. Не увеличивать крупные файлы без объяснения и плана в TODO; срочное исправление не блокировать искусственным рефакторингом. `partial class` полезен для организации, но не заменяет разделения ответственности; не дробить ради числа строк, не удалять комментарии и не уплотнять код ради метрики. Выделять тестируемые сервисы, модели, команды, контролы и словари ресурсов по назначению; сохранять поведение, паритет Python, транзакции, очередь сохранения и SQL Pilot guard. Генерируемые/вендорные файлы и артефакты исключать с документированным основанием. В отчёте указывать размеры до/после затронутых крупных файлов, новые исключения и реальные проверки. План и критерии: [ARCHITECTURE_SIZE_TODO](docs/ARCHITECTURE_SIZE_TODO_20261126.md). Не менять приоритет текущего переноса/SQL без решения владельца.
